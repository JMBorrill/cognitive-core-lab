Study 01 is untouched apart from two behaviour-preserving edits: the framework-free helpers moved from

under MLX's Linux build.

### 2.1 Three details of the port that matter

1. **MLX's Adam applies no bias correction by default.** Study 01's `lr 1e-5` therefore took steps two to six
   times larger than PyTorch's AdamW would at the same setting. The reproduction uses the uncorrected update;
   the conventional settings use the standard one.
2. **The checkpoint ships with sampling switched on** (`do_sample`, temperature 0.7, repetition penalty 1.1).
   MLX ignored those defaults; `transformers` applies them unless told otherwise. The port switches them off.
3. **MLX-LM's `scale` is not PEFT's `alpha`.** Scale 20 at rank 16 is `lora_alpha = 320`.

Checks made on CPU before any GPU was used, all part of the test suite:

- With the real tokenizer and weights, the port sees the same number of tokens and supervised tokens as the
  Study 01 log on **all 250 steps** of variants B and C, and computes the same loss before any update
  (0.5565 against 0.5562 for C, 0.4104 against 0.4122 for B).
- 5,865,472 trainable parameters for the Study 01 layout, as reported.
- Loss covers assistant tokens only; a packed episode equals its per-turn examples; batched greedy decoding
  equals unbatched; an interrupted run resumes to the same adapter; the optimizer matches a reference
  implementation in both modes and equals `torch.optim.AdamW` in the corrected mode.

## 4. The v2 environment

### 4.1 Schema, tools and families

One schema lists 12 domains, 37 entity types, their attributes and 60 references between them. From it
`ccl/world2.py` derives **122 tools** (37 look-ups by ID, 18 searches by name, 39 list tools, 20
state-changing actions, 8 back-up look-ups), each simulated by one of five generic functions. No domain, tool
or identifier prefix is shared with Study 01. The proposal expected about 80 tools; the schema needed more
references than first drafted to give a practice space of 5,000 families, and each listable reference adds a
tool.

A **family** is one gold dependency graph: the role, the expected status, the calls with their
dependencies, and the faults. It is Study 01's graph signature with one refinement: a tool that fails once
(retry) and a tool that is down (fallback) are different families. Study 01's signature merges them, which is
why its 24 templates had 23 signatures.

What does and does not make a new family is fixed in `ccl/compose.py` and enforced by tests:

- Two families always differ in which tools are called, in how the calls depend on each other, or in the
  behaviour required (retry, fallback, stop on not-found, stop on a denied approval, refuse for lack of role).
- Wording, concrete values, the attribute asked for, the rule that picks a record from a list (lowest, highest,
  matching), distractor tools and the order of independent calls never make a new family.
- A base graph has at most one retry variant and one fallback variant; the failing call is fixed by a hash, so
  the position of a fault does not multiply families.
- "The same question about two records at once" is a family only for paths of at most two calls.
- Requests about a record that does not exist share one family per first call, whatever would have followed.

### 4.2 Splits

Hold-outs are assigned by hash, not by hand. Two domains (insurance, property) are reserved for
`test_domain` and one (hotel) for `dev`; 8 tools for `test_tool` and 4 for `dev`; 63 of the 317 edges between
practice tools for `test_comp` and 25 for `dev`. An edge is held out only if both of its tools stay practised
through other edges. A tool belongs to every domain it touches, so a practice task cannot even list records by
the ID of a held-out entity.

### 4.3 Controls on validity

| risk | control | evidence |
|---|---|---|
| distinct families that are really the same structure | family identity is the gold graph; one fault variant per graph; twins only for short paths | `tests/test_v2.py` |
| difficulty drifting with the number of families | every nested subset has the same mix of hops and modifiers | 2.8-2.9 gold calls per task at every level; table in §5 |
| D confounded with tool and edge coverage | not removable by design; both recorded per run, and success reported for families the run's training set covers | §5.3 |
| test structure leaking into training | one split per family; training reads `data/v2/practice` only; scoring is a separate script | `test_no_held_out_structure_reaches_training_inputs` |
| test instances leaking into training | disjoint ID ranges and name lists for training and evaluation instances | 0 shared record IDs and 0 shared requests in the build's audit |
| tuning on test data | settings fixed in Experiment 0 on Study 01's validation tasks; nothing tuned in Experiment 1; every access to a sealed split logged | `results/study02/test_access.jsonl` |
| tasks that penalise defensible behaviour | oracle and degenerate-policy gate; manual read of about 100 requests; reference-model gate | `data/v2/gate/README.md` |
| the generator's style being what is learned | v1 anchor (hand-written tasks and tools, never trained on); phrase variants reserved for evaluation | §5.2 |

Two defects were found and fixed by reading generated tasks before the data were frozen: a fan-out could
overwrite the reference that a list had just used (an inconsistent world, caught because the oracle then used
an ID it had not observed), and nested requests were ambiguous about which noun a selection rule applied to
(every phrase now ends in the noun phrase it builds on, so requests are right-branching). A later read found
that a question could ask for the attribute its own rule had stated, and that a list tool keyed by a held-out
entity was still a practice tool; both were fixed before freezing.

The reference-model step of the quality gate turned out weaker than planned and is described honestly in
[`data/v2/gate/README.md`](../../data/v2/gate/README.md): `Qwen2.5-7B-Instruct` solved 3% of four-hop tasks
through its own errors, so it could vouch only for shallow families. No family was removed.

## 9. Reproducing this report

```bash
uv venv --python 3.11 .venv && uv pip install --python .venv/bin/python -r requirements-cuda.lock
.venv/bin/python -m pytest -q                       # CPU; includes the byte-for-byte rebuild of data/v1 and data/v2
.venv/bin/python scripts/s2_prepare_v1.py           # Study 01 training files, checked against their hashes
.venv/bin/python scripts/s2_train.py configs/study02/e1/<run>.json --out runs2      # GPU
.venv/bin/python scripts/s2_score.py configs/study02/e1/<run>.json --out runs2      # GPU
.venv/bin/python scripts/s2_analyze.py e0 && .venv/bin/python scripts/s2_analyze.py e1 && .venv/bin/python scripts/s2_analyze.py books
```

Per-run records are in `results/study02/runs/<experiment>/<run>/`: the per-episode metrics, the training log,
the configuration with data hashes, the adapter's SHA-256, the code commit, library versions and GPU.
Adapters, checkpoints and per-episode traces are in the private storage bucket `JMBorrill/ccl-study02`.
Seeds: replicate *r* uses seed *r* for the family subset, the LoRA initialisation and the batch order.
